# ReverseAI — продуктовая спецификация

> **Статус:** черновик v0.1 (2026-10-20), ждёт правок основателя.
> **Как читать:** это живой документ и единый источник правды для всех чатов и агентов, работающих над проектом.
> Принятые решения дублируются в [`decisions.md`](decisions.md) с номерами `D-xxx`.
> Метки в тексте:
> - **[РЕШЕНО D-xxx]** — решение основателя, менять только новым решением в журнале.
> - **[ПРЕДП]** — предположение автора черновика; основатель подтверждает или правит.
> - **[ОТКРЫТО]** — вопрос без ответа; блокирует соответствующую часть реализации.
>
> Основа: исследование [`docs/research/report.ru.md`](../research/report.ru.md).

## 1. Видение

ReverseAI — платформа ИИ-агентов, которая изучает работающее программное обеспечение **как чёрный ящик** (поведение, интерфейс, сетевой обмен, документацию, форматы данных) и выпускает **независимую реимплементацию** с эквивалентной функциональностью: новый код, написанный без доступа к исходному или декомпилированному коду оригинала. **[РЕШЕНО D-001, D-005]**

Главный тезис из исследования: ценность продукта — не в генерации кода (её коммодитизируют Anthropic, OpenAI, AWS), а в трёх вещах, которые мы строим сами:

1. **Оракул поведения** — исполняемый набор сценариев и проверок, снятых с оригинала, по которому измеряется, что новая система делает то же самое.
2. **Информационный барьер** — доказуемая изоляция агентов, видевших оригинал, от агентов, пишущих код.
3. **Доказательства** — метрики паритета и пакет документов о независимости результата, пригодный для юриста заказчика.

LLM — заменяемый исполнитель внутри этой системы.

## 2. Клиенты и сценарии

**[РЕШЕНО D-002]** Первые клиенты: компании с legacy-системами и рынок импортозамещения в РФ.

### 2.1. Сценарий «Legacy» — своя устаревшая система

- **Кто:** компания, у которой есть внутреннее веб-приложение на устаревшем стеке (например, старая Java/PHP/ASP.NET/Delphi-web система), без актуальной документации, с уходящими экспертами.
- **Что хочет:** та же функциональность на современном поддерживаемом стеке.
- **Особенность:** система принадлежит заказчику, поэтому юридический риск минимален. Заказчик может дать тестовый стенд, копию БД, доступ к логам — это сильно улучшает оракул. **[ПРЕДП]** Даже здесь агенты-реализаторы не получают исходный код: так продукт остаётся единым по процессу, а заказчик получает чистую спецификацию, которой у него раньше не было.
- **Что важно заказчику:** паритет бизнес-логики, перенос данных, сроки, отсутствие регрессий.

### 2.2. Сценарий «Импортозамещение» — замена чужого продукта

- **Кто:** компания или вендор в РФ, которым нужно заменить иностранный веб-продукт (SaaS или коробочное веб-ПО), ушедший с рынка или ставший недоступным.
- **Что хочет:** собственный продукт с эквивалентной функциональностью, совместимый по данным (импорт/экспорт, форматы, API для интеграций).
- **Особенность:** продукт чужой. Работает строгий режим чистой комнаты: наблюдение только через законно полученный доступ (свой аккаунт, своя лицензия), никакого брендинга и текстов оригинала в результате, отдельная проверка патентов и товарных знаков.
- **Что важно заказчику:** миграция пользователей и данных, совместимость форматов, юридическая чистота.

### 2.3. Кто работает с платформой

| Роль | Что делает |
|---|---|
| Владелец проекта (заказчик) | Подаёт цель, подтверждает законность доступа, утверждает спецификацию, принимает результат |
| Аналитик / доменный эксперт заказчика | Отвечает на вопросы агентов, подтверждает бизнес-правила |
| Юрист заказчика | В конвейере не участвует; получает итоговый пакет доказательств после аудита **[РЕШЕНО D-010]** |
| Оператор платформы (наша команда) | **[ПРЕДП]** В MVP сопровождает каждый проект вручную (сервисная модель), дальше — самообслуживание |

## 3. Цели, не-цели, анти-цели

### Цели MVP
- Для веб-приложения **[РЕШЕНО D-003]** пройти весь путь: наблюдение → оракул → спецификация → барьер → реализация → проверка паритета → пакет доказательств.
- Измеримый результат: процент прохождения оракула новой системой, стоимость проекта, отчёт о сходстве кода.
- Завершить 1–2 платных пилота **[ПРЕДП]**.

### Не-цели MVP
- Десктоп, мобильные приложения, библиотеки/CLI — позже **[РЕШЕНО D-003]**.
- Декомпиляция и анализ бинарников **[РЕШЕНО D-005]**.
- Собственная модель — только при явной потребности **[РЕШЕНО D-004]**.
- On-prem поставка платформы **[ПРЕДП]**.
- Полное самообслуживание без участия оператора **[ПРЕДП]**.

### Анти-цели (провал, даже если «работает»)
- **Визуальная копия.** Клон, неотличимый по виду от оригинала (логотипы, цвета, макеты, тексты). Цель — функциональный паритет, а не внешний: это защищает от претензий по trade dress и товарным знакам.
- **Утечка выражения оригинала** в код результата: фрагменты JS-бандлов, SQL, тексты интерфейса, ассеты.
- **Паритет «по меню»** — когда все кнопки на месте, но поведение не совпадает (урок ArtCraft: «measures wiring, not behaviour»).
- **Вред цели наблюдения:** нагрузка на чужой продакшен, действия от имени реальных пользователей, изменение чужих данных.
- **Отмывание лицензий OSS** как сценарий использования.

## 4. Принципы

1. **Оракул важнее модели.** Любое улучшение сначала проверяем: поднимает ли оно процент прохождения оракула и снижает ли цену проекта.
2. **Только чёрный ящик** **[РЕШЕНО D-005]**. Источники: наблюдаемое поведение, сетевой обмен, документация, данные и форматы, ответы экспертов заказчика.
3. **Две зоны.** «Грязная» зона видит оригинал, «чистая» зона пишет код. Между ними — только утверждённая спецификация и тесты.
4. **Всё записывается.** Что видел каждый агент, какая модель, какие промпты и инструменты — в неизменяемом журнале.
5. **Модельная независимость.** Любой агент работает через единый шлюз и может сменить провайдера без изменения кода.
6. **Считаем цену решённой задачи**, а не цену токена.
7. **Человек утверждает переходы** между фазами в MVP.

## 5. Сквозной процесс

```
 ┌──────────── «грязная» зона ─────────────┐   барьер   ┌──────── «чистая» зона ────────┐
 Приём → Наблюдение → Оракул → Спецификация → Очистка+ → Реализация → Проверка паритета → Поставка
 цели                                         подпись     (код)        (на оригинале и       + пакет
                                                                          на клоне)          доказательств
```

| # | Фаза | Вход | Выход | Кто утверждает |
|---|---|---|---|---|
| 0 | Приём цели | Заявка заказчика | Карточка проекта, аттестация законности, режим (legacy / импортозамещение), границы | Оператор + заказчик |
| 1 | Наблюдение | Доступ к цели | Сырой корпус наблюдений | — |
| 2 | Оракул | Корпус наблюдений | Воспроизводимые сценарии и проверки | Оператор |
| 3 | Спецификация | Корпус + оракул + ответы экспертов | Поведенческая спецификация | Аналитик заказчика |
| 4 | Барьер | Спецификация + тесты | Очищенный пакет для чистой зоны | Оператор или аналитик заказчика **[РЕШЕНО D-010]** |
| 5 | Реализация | Только очищенный пакет | Код новой системы | — |
| 6 | Проверка паритета | Клон + оригинал + оракул | Отчёт о паритете, контрпримеры | Цикл 5↔6 до порога |
| 7 | Аудит и поставка | Код + журнал | Репозиторий, отчёт о сходстве, пакет доказательств | Оператор + заказчик |

Цикл 5↔6 повторяется автоматически: расхождения превращаются в **обезличенные** описания ошибок («при вводе X ожидается результат Y, получено Z») и возвращаются реализаторам. Расхождения не несут кода или текстов оригинала.

## 6. Компоненты

### 6.1. Приём цели (юридический шлюз)
- Анкета: что за система, кто правообладатель, на каком основании у заказчика доступ, юрисдикция заказчика.
- Аттестация заказчика о законном доступе (галочка + подпись в договоре).
- Режимы: **legacy** (своя система) и **импортозамещение** (чужая).
- Для режима «импортозамещение»: предупреждение о патентах и товарных знаках, чек-лист условий использования оригинала (запрет автоматизированного доступа и реверса в ToS/EULA), флаг риска.
- Границы наблюдения: список разрешённых доменов, тестовые аккаунты, запрет на действия в продакшене (если это не изолированный стенд).

### 6.2. Наблюдение (грязная зона)

Для веб-цели **[РЕШЕНО D-003]** используются такие источники:

| Источник | Инструмент | Что собираем |
|---|---|---|
| UI-исследование | Браузерный агент на Playwright **[ПРЕДП]** | Карта экранов и переходов, пользовательские сценарии, поля форм, валидации, сообщения об ошибках, состояния |
| Сетевой обмен | Перехватывающий прокси (mitmproxy) **[ПРЕДП]** | HTTP/WebSocket-запросы и ответы → контракты API, модели данных, коды ошибок |
| Документация | Загрузка файлов, справка, публичная документация | Описание функций, бизнес-правила |
| Данные | Экспорты, выгрузки, у legacy — схема и копия БД | Сущности, связи, форматы, инварианты |
| Эксперты | Чат-вопросы агентов к аналитику заказчика | Подтверждение правил, ответы на неоднозначности |

Обязательные правила:
- **JS/CSS-бандлы и любой исполняемый код оригинала** при сохранении помечаются как «выражение» и **никогда** не попадают ни в спецификацию, ни в чистую зону. Агенты наблюдения используют их только для навигации.
- Ассеты (изображения, шрифты, иконки) не сохраняются в корпус, только факт их наличия.
- Ограничение частоты запросов к цели; никаких нагрузочных и деструктивных действий вне выделенного стенда.
- Учётные данные цели хранятся в хранилище секретов, не попадают в промпты в открытом виде.

### 6.3. Оракул
- **Сценарии:** записанные пользовательские пути, нормализованные в воспроизводимые тесты, которые запускаются одинаково на оригинале и на клоне через абстрактный слой «драйвера приложения». Тесты привязаны к **смыслу** (поля, действия, данные), а не к селекторам и вёрстке оригинала.
- **Контракты API:** OpenAPI-описание, выведенное из трафика, плюс примеры запросов и ответов как контрактные тесты. **[ПРЕДП]** В режиме импортозамещения совместимость по API — опция заказчика: если она не нужна, проверяется только функциональный результат.
- **Инварианты данных:** правила вида «после действия A в сущности B появляется запись с полями…».
- **Детерминизм:** оракул нормализует нестабильные поля (даты, ID, порядок). Для сценариев, которые нельзя воспроизвести без сброса состояния, нужен стенд с откатом. Для legacy это копия стенда заказчика, для импортозамещения — песочница или отдельный аккаунт. **[ОТКРЫТО]** Как работаем, если у чужого SaaS нет способа сбросить состояние.
- **Метрика покрытия оракула:** доля функций спецификации, у которых есть хотя бы одна проверка.

### 6.4. Спецификация
Формат — структурированный Markdown + YAML **[ПРЕДП]**:
- функции и пользовательские сценарии;
- сущности и модель данных;
- бизнес-правила и валидации;
- контракты API (если нужна совместимость);
- нефункциональные требования (роли и права, производительность, локализация);
- у каждого пункта: **ссылки на наблюдения** (прослеживаемость), **уровень уверенности**, явные **пробелы** («не наблюдали, нужен ответ эксперта»).

Спецификацию пишут агенты-аналитики, проверяет агент-критик, утверждает аналитик заказчика.

### 6.5. Барьер (очистка и подпись)
- Автоматическая очистка: удаление фрагментов кода, минифицированных идентификаторов, длинных дословных текстов оригинала, названий бренда, URL оригинала.
- Тексты интерфейса: в спецификацию попадает **смысл** сообщения, а не формулировка. **[ПРЕДП]** Исключение — технически значимые строки (имена полей в форматах обмена, коды ошибок API), они нужны для совместимости.
- Проверка сходства: автоматическое сравнение спецификации с корпусом выражения оригинала (n-граммы по коду и текстам), порог блокировки.
- Подпись: оператор платформы или аналитик заказчика утверждает каждую версию пакета (подпись привязана к SHA-256 пакета). Подпись фиксируется в журнале. Юрист в конвейере не участвует и получает итоговый пакет доказательств **[РЕШЕНО D-010]**.
- В чистую зону передаются: спецификация, тесты оракула **без** записанных ответов оригинала (только ожидаемый смысл), целевой стек.

### 6.6. Реализация (чистая зона)
- Отдельная песочница: свой контейнер, свои API-ключи, нет сетевого доступа к цели, нет общей памяти и векторного хранилища с грязной зоной.
- Агенты: планировщик (раскладывает спецификацию на задачи), исполнители (параллельно), агент-судья (проверяет готовность), ревьюер.
- Критерий завершения задачи — явный: тесты оракула по этой функции зелёные. Есть защита от преждевременной остановки (урок NL2Repo).
- Целевой стек MVP: **[ПРЕДП]** один стек на старте, TypeScript (Next.js) + PostgreSQL, чтобы накопить шаблоны и качество. **[ОТКРЫТО]** Выбирает ли заказчик стек.
- Новый продукт получает новое имя и собственный нейтральный дизайн.
- Каждая функция результата доступна через единый реестр команд (CLI/API) **[ПРЕДП]**, по образцу PhotoCraft: так клон удобно проверять агентами.

### 6.7. Проверка паритета
- Прогон одних и тех же сценариев на оригинале и на клоне, сравнение результатов на уровне данных и поведения, **не пикселей**.
- Расхождения → обезличенные отчёты об ошибках → обратно в чистую зону.
- Отчёт о паритете: % сценариев пройдено, по функциям, по критичности; список известных расхождений.
- **[ПРЕДП]** Порог приёмки по умолчанию: 95% сценариев и 100% сценариев, помеченных критичными; конкретику согласуем в договоре.

### 6.8. Аудит и поставка
- Проверка сходства кода результата с любым кодом оригинала, попавшим в корпус (JPlag/MOSS-подобный инструмент + n-граммы).
- Проверка лицензий зависимостей и фрагментов из OSS.
- Проверка ассетов и упоминаний бренда.
- **Пакет доказательств:** журнал процесса (что видела каждая зона), версии спецификации с подписями, отчёт о сходстве, отчёт о паритете, перечень моделей и версий.
- Поставка: репозиторий с кодом, спецификация, тесты, инструкция по развёртыванию, план миграции данных **[ПРЕДП]**.

### 6.9. Журнал провенанса
- Append-only журнал с хеш-цепочкой: каждое событие (вызов модели, вызов инструмента, чтение артефакта, передача через барьер, подпись).
- У каждого артефакта: зона, источник, хеш.
- Экспорт в читаемый отчёт для юриста.

## 7. Модельный слой

**[РЕШЕНО D-004]** Китайские и американские API через хостинг за рубежом; позже — свои открытые веса; маленькая своя модель — только при явной потребности.

### 7.1. LLM-шлюз
- Единая точка для всех агентов: нормализация форматов (Anthropic-совместимый и OpenAI-совместимый), повтор и переключение при ошибках 429/5xx, учёт токенов и стоимости по проекту, фазе, роли и агенту.
- **[ПРЕДП]** Основа — LiteLLM или аналог с собственной обвязкой; готового скилла для этого нет, пишем сами.
- Политика данных проекта определяет **допустимых провайдеров**: например, «только США/ЕС» или «китайские API разрешены». Шлюз отклоняет запрос к запрещённому провайдеру.

### 7.2. Роли и модели (стартовая конфигурация **[ПРЕДП]**)

| Роль | По умолчанию | Дешёвая альтернатива | Комментарий |
|---|---|---|---|
| Планировщик, судья, критик спецификации | Claude Opus 5.5 | GPT-6.1 Sol | Мало вызовов, высокая цена ошибки |
| Исполнитель (код, анализ) | Claude Sonnet 5.5 | GPT-6.1 Sol, DeepSeek V4 Pro, GLM-5.3 | Основной объём работы |
| Массовые задачи (суммаризация наблюдений, нормализация трафика, генерация тестов) | Claude Haiku 5.5 / GPT-6 Luna | DeepSeek V4.1 Flash | Если политика данных разрешает |
| Браузерный агент наблюдения | **[ОТКРЫТО]** выбрать по бенчмарку | — | Нужен замер на наших целях |

Конфигурация хранится в файле, а не в коде. Решение о смене модели принимается по **стоимости успешно пройденного оракула** на нашем внутреннем бенчмарке (раздел 10).

### 7.3. Собственная модель
- В MVP не делаем.
- **С первого дня сохраняем траектории** (наблюдение → спецификация → код → результат оракула) как будущий датасет. Это требует согласия заказчика в договоре **[ОТКРЫТО]**.
- Кандидаты на дообучение, когда появятся данные: нормализация трафика в контракты API, генерация тестов оракула, узкий исполнитель для целевого стека.

## 9. Платформа

### 9.1. Интерфейс
- Веб-консоль: проекты, фазы и их статус, карта наблюдений, спецификация с комментариями и подписью, отчёт о паритете, расходы, пакет доказательств.
- Вопросы агентов к экспертам заказчика — прямо в консоли.
- **[ПРЕДП]** Для MVP интерфейс минимальный; основную работу ведёт оператор.

### 9.2. Технологический стек платформы **[ПРЕДП]**
- Оркестрация агентов и бэкенд: Python.
- Долгие процессы (часы и дни): движок устойчивых процессов (например, Temporal).
- Песочницы: Docker на старте, позже — микро-ВМ для жёсткой изоляции.
- Хранилища: PostgreSQL (метаданные, журнал), объектное хранилище S3-совместимое (корпус наблюдений, артефакты).
- Наблюдение: Playwright, mitmproxy.
- Консоль: TypeScript + Next.js.
- Наблюдаемость LLM: Langfuse или аналог.
- Хостинг: облако за пределами РФ **[РЕШЕНО D-004 — частично]**; **[ОТКРЫТО]** конкретный провайдер и юрисдикция юрлица.

### 9.3. Безопасность данных заказчика
- Шифрование корпуса наблюдений; изоляция проектов разных заказчиков.
- Секреты цели в хранилище секретов.
- Срок хранения данных проекта и удаление по запросу.
- Политика провайдеров LLM на уровне проекта (см. 7.1).

## 10. Внутренний бенчмарк

В литературе нет бенчмарка полного цикла «наблюдение → спецификация → реализация». Строим свой:
- 5–10 веб-приложений с открытым кодом **[ПРЕДП]** (разной сложности: CRUD, документооборот, CRM-подобное), которые мы разворачиваем сами. Их код используем **только** как скрытый эталон для оценки и никогда не показываем агентам.
- Метрики: % пройденных скрытых сценариев, стоимость, время, сходство кода с оригиналом.
- Используется для выбора моделей, регрессий платформы и в маркетинге.

## 16. Глоссарий
- **Оракул** — набор исполняемых проверок, задающий правильное поведение по наблюдениям за оригиналом.
- **Грязная зона** — агенты и данные, имеющие доступ к оригиналу.
- **Чистая зона** — агенты, пишущие код только по утверждённой спецификации.
- **Барьер** — очистка и подпись спецификации перед передачей в чистую зону.
- **Паритет** — доля сценариев оракула, которые новая система проходит так же, как оригинал.
- **Пакет доказательств** — документы, подтверждающие независимость реимплементации.
- **Выражение** — охраняемая авторским правом форма оригинала: код, тексты, графика, дизайн.
