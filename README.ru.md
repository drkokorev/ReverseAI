# ReverseAI

[English](README.md) · **Русский**

> **Статус:** завершённый исследовательский прототип, опубликован как open source под лицензией [MIT](LICENSE). Активно не развивается. Скриншоты веб-консоли — в [README на английском](README.md#screenshots) и в [`docs/console-screenshots/`](docs/console-screenshots/).

ReverseAI — платформа ИИ-агентов для clean-room реимплементации веб-приложений: функциональность существующего ПО воссоздаётся независимым кодом, без копирования исходного кода (D-001). Цель изучается только как «чёрный ящик» — по поведению, HTTP-трафику и интерфейсу; декомпиляция и разбор кода цели не используются (D-005). Код клона пишут агенты в отделённой «чистой» зоне, которая видит только согласованный человеком пакет (спецификацию и сценарии), а не оригинал. Отделение обеспечивается по данным — хранилище артефактов не выдаёт чистой зоне ничего из dirty; сам код клона в прототипе выполняется в `LocalSandbox` на машине оператора без изоляции (см. «Ограничения прототипа»).

Это прототип первой стадии (веб-цели, шаблон клона на Python/FastAPI). Он не является юридической консультацией: допустимость реимплементации конкретного продукта должен оценивать юрист.

## Конвейер

```
 intake ──► observe ──► oracle ──► spec ──► prepare-release ──► approve / release
 (dirty)    (dirty)     (dirty)    (dirty)   (dirty → draft)     человек + барьер
                                                                      │
                                                                      ▼ (released)
                          audit ◄──────── build loop ─────────────────┘
                        (verifier)   implement (clean) ◄──► parity (verifier)
```

| Этап | Команда | Зона | Что происходит |
|------|---------|------|----------------|
| intake | `init` | dirty | юридический фильтр: аттестация законного доступа, разрешённые домены, проверка бренда |
| observe | `observe` | dirty | обход цели в браузере (Playwright), запись HAR; нажатие кнопок и флажков вне форм и зондирование API — только для песочницы |
| oracle | `oracle` | dirty | из наблюдений строятся исполнимые поведенческие сценарии |
| spec | `spec` | dirty | аналитик + критик (LLM) составляют поведенческую спецификацию |
| prepare-release | `prepare-release` | dirty → черновик | санитайзер очищает спецификацию и сценарии; черновик для согласования (спецификация, все выпускаемые сценарии, список удержанных ожидаемых значений) и SHA-256 пакета |
| approve / release | `approve` | released | человек согласует пакет по его SHA-256; барьер выпускает в чистую зону спецификацию и сценарии |
| implement | `build` | clean | агент пишет клон по выпущенному пакету в рабочем каталоге вне каталога проекта (`<projects-root>/.workspaces/<случайное имя>`) |
| parity | `build` | verifier | оригинал проверяется полными сценариями, клон — их выпущенной версией (удержанные барьером значения от клона не требуются); в чистую зону уходит только обезличенная обратная связь |
| audit | `audit` | verifier | сходство кода клона с оригиналом, пакет доказательств (zip) |

Шаги implement и parity повторяются в цикле (`--max-rounds`), пока паритет не достигнет порога (по умолчанию 95% всех сценариев и 100% критичных) или раунды не закончатся. Сценарии, которые не проходят на самом оригинале, считаются нестабильными и в долю не входят, но порог не достигается, если нестабилен хотя бы один критичный сценарий или нестабильных больше 20%.

## Быстрый старт

```bash
uv sync
uv run playwright install chromium      # браузер для наблюдения
uv run pytest                           # быстрые тесты (без live; browser/docker пропускаются, если недоступны)
uv run pytest -m browser tests/e2e      # полный офлайн-e2e: весь конвейер на эталонной цели, LLM заменён сценарной моделью
uv run reverseai bench --target taskboard --live   # то же с реальными моделями (нужны ключи, см. ниже)
```

`bench --live` запускает весь конвейер на встроенной эталонной цели `taskboard` (каталог `bench/targets`), автоматически «согласует» выпуск от имени оператора бенчмарка и печатает метрики: паритет, скрытые тесты, максимальное сходство кода, стоимость. Без `--live` команда завершается с ошибкой: офлайн-прогон выполняется только в тестах.

## Работа с реальным проектом

Все команды принимают `--project <каталог проекта>`. Проект создаётся внутри `--projects-root` в подкаталоге с именем, полученным из названия (`Acme Orders` → `projects/acme-orders`).

### 1. Карточка проекта

`card.yaml`:

```yaml
name: Acme Orders                        # название проекта
mode: legacy                             # legacy | import_substitution
target_base_url: https://orders.acme.example/
allowed_domains:                         # хост из target_base_url обязан быть в списке
  - orders.acme.example
target_is_sandbox: false                 # true только для тестового стенда: тогда разрешены POST и зондирование API
attestation:                             # подтверждение законного доступа
  lawful_access: true
  basis: "Договор №42 от 2026-09-01, п. 5: право на анализ и реимплементацию"
  signed_by: "Иванов И. И., юрист заказчика"
  signed_at: "2026-10-20T10:00:00+00:00"
data_policy:                             # необязательно; по умолчанию us, eu, self
  allowed_jurisdictions: [us, eu, self]
jurisdiction: RU
brand_terms:                             # слова бренда оригинала, которые нельзя повторять в названии клона
  - Acme Orders
  - Acme
product_name: OrderFlow                  # название клона
target_stack: python-fastapi             # единственный поддерживаемый шаблон
```

Название продукта, повторяющее `brand_terms`, хост вне `allowed_domains`, аттестация с `lawful_access: false` и неизвестный ключ карточки (например, опечатка `brand_term`) отклоняются на этапе `init`.

### 2. Прогон по шагам

```bash
# 1. Приём: создаёт projects/acme-orders и печатает флаги риска
uv run reverseai init --card card.yaml --projects-root projects

P=projects/acme-orders

# 2. Наблюдение (--submit-forms и --probe допустимы только если target_is_sandbox: true)
uv run reverseai observe --project $P --max-pages 50

# 3. Оракул и спецификация (спецификация вызывает LLM)
uv run reverseai oracle --project $P
uv run reverseai spec --project $P

# 4. Черновик выпуска: печатает путь к черновику и SHA-256 пакета (спецификация + сценарии)
uv run reverseai prepare-release --project $P
# Прочитайте черновик. Затем согласуйте именно эту версию (хэш обязан совпасть):
uv run reverseai approve --project $P --approver "Иванов И. И." --role customer_analyst --sha <SHA-256 пакета>

# 5. Реализация и паритет (код выхода 2, если порог не достигнут)
uv run reverseai build --project $P --max-rounds 3

# 6. Аудит сходства и пакет доказательств (код выхода 2, если сходство выше порога
#    или в коде клона есть слова бренда)
uv run reverseai audit --project $P --out evidence/
```

Роль согласующего — `operator` (оператор платформы) или `customer_analyst` (аналитик заказчика; проверяет, что в спецификации и сценариях нет кода, текстов и бренда оригинала). Юрист заказчика в конвейере не участвует и получает итоговый пакет доказательств после аудита (D-010). Хэш пакета привязывает согласование к конкретному черновику — и к спецификации, и к сценариям: если изменилось хоть что-то из них, `--sha` не совпадёт и выпуск не пройдёт.

Если цель — песочница, а выпущенные сценарии изменяют данные (POST/PATCH/DELETE…), `build` откажется запускаться: командная строка не умеет сбрасывать цель между сценариями, и паритет был бы нестабилен. Флаг `--allow-unstable` запускает проверку всё равно. Если цель не песочница, сценарии с записью при проверке паритета пропускаются (в отчёте — «пропущено сценариев с записью»).

Служебные команды:

```bash
uv run reverseai status --project $P          # завершённые этапы и ссылки на артефакты
uv run reverseai costs --project $P           # расходы на LLM по ролям и моделям
uv run reverseai ledger-verify --project $P   # проверка целостности журнала происхождения
```

Этапы выполняются строго по порядку; при нарушении порядка команда сообщит, какой этап нужно завершить. Повторный запуск этапа сбрасывает все последующие (в журнале — событие `phase.invalidated`): например, после повторного `oracle` нужно заново пройти `spec`, `prepare-release` и `approve`.

## Веб-консоль

Те же этапы можно вести из браузера:

```bash
uv run reverseai console --projects-root projects/ --operator "Иван Иванов"
# Консоль ReverseAI: http://127.0.0.1:8765
```

- **Проекты** — все проекты каталога: режим, хост цели, пройденные этапы (из 9), последняя активность; форма нового проекта проходит тот же юридический фильтр, что `reverseai init`, ошибки показываются рядом с формой.
- **Обзор проекта** — траектория девяти этапов со временем и итогом каждого, показатели (паритет, критичные сценарии, сходство кода, стоимость LLM), зоны с числом артефактов, журнал происхождения (последние события, фильтр по типу, короткие хэши) и проверка его целостности. Здесь же запускаются этапы: наблюдение, оракул, спецификация, подготовка выпуска, реализация с паритетом, аудит. Каждый этап — фоновая задача (одна на проект), страница сама обновляет её статус и журнал вывода; ошибки показываются по-русски, как в командной строке.
- **Согласование** — вкладки «Спецификация», «Сценарии», «Очистка» (находки санитайзера, удержанные значения, отброшенные оракулом сценарии) и SHA-256 пакета. Согласует оператор платформы или аналитик заказчика; флажок подтверждения обязателен, подпись привязана к хэшу показанного черновика.
- **Паритет** — итоги и таблица сценариев, сходство кода с порогом, упоминания бренда, состав пакета доказательств и кнопка скачивания архива для юриста заказчика.
- **Расходы** — вызовы LLM и стоимость по ролям и моделям (те же числа, что `reverseai costs`).

Консоль вызывает те же функции конвейера, что и команды CLI, поэтому записи в журнале одинаковы. Аудит из консоли кладёт пакет доказательств в `<проект>/evidence/`. Ключи провайдеров берутся из переменных окружения; если ни одного нет, этап «Спецификация» сообщит об этом, не вызывая модели. Чтение артефактов для показа пишется в журнал один раз за запуск консоли; в обзоре такие события (`artifact.*`) по умолчанию скрыты — чип «показать артефакты» возвращает их. Консоль читает проект с диска на каждый запрос, поэтому правки `card.json` действуют сразу. CLI и консоль можно запускать одновременно: изменяющие команды и задачи берут блокировку проекта `<проект>/pipeline.lock` (D-015), и вторая такая операция сразу получает отказ «проект занят другим процессом» (CLI — код выхода 1), а не ждёт и не портит состояние. Если аудит запущен из CLI с другим `--out`, страница паритета сообщает, что пакет собран вне консоли, и не показывает старый.

Тема (тёмная или светлая) по умолчанию следует настройке системы, переключатель в шапке её запоминает.

По умолчанию консоль слушает только `127.0.0.1` и проверяет заголовок Host. Для другого адреса нужен токен:

```bash
export REVERSEAI_CONSOLE_TOKEN=$(openssl rand -hex 24)
uv run reverseai console --projects-root projects/ --host 0.0.0.0 --port 8765
# вход в браузере: http://<адрес>:8765/login (форма для токена), либо заголовок Authorization: Bearer <токен>
```

Без токена на не-loopback адресе консоль не запустится. Токен передаётся только формой (POST), не в адресе; журнал запросов сервера не записывает строки запроса. Формы защищены CSRF-токеном, политика безопасности контента разрешает только собственные файлы и шрифты Google; всё, что пришло от цели, экранируется. Снимки всех страниц в обеих темах — в [`docs/console-screenshots/`](docs/console-screenshots/).

## Провайдеры моделей

Ключи читаются из переменных окружения и никогда не попадают в журнал, артефакты, промпты и окружение песочницы:

| Переменная | Провайдер | Юрисдикция |
|------------|-----------|------------|
| `ANTHROPIC_API_KEY` | Anthropic | us |
| `OPENAI_API_KEY` | OpenAI | us |
| `DEEPSEEK_API_KEY` | DeepSeek | cn |
| `ZAI_API_KEY` | Z.ai (GLM) | cn |

Политика данных по умолчанию — `us`, `eu`, `self`: китайские провайдеры (`cn`) отключены. Чтобы разрешить их, добавьте `cn` в `data_policy.allowed_jurisdictions` в карточке проекта; шлюз выбирает для роли только кандидатов из разрешённых юрисдикций, а если таких нет, вызов отклоняется (`PolicyViolation`). Модели, цены и маршрутизация ролей — в `src/reverseai/config/default.yaml`; идентификаторы моделей помечены `# verify id` и требуют проверки перед боевым использованием.

## Правила зон

- **dirty** — всё, что получено от оригинала: HAR, ответы, тексты страниц, JS/CSS. Читать может только dirty и released.
- **released** — спецификация и сценарии, прошедшие санитайзер и согласованные человеком через барьер. Единственный путь информации из dirty в clean. Санитайзер очищает текстовые поля полностью (код, дословные фрагменты оригинала, бренд, домены), а в идентификаторах, путях API и телах запросов маскирует только бренд и домены — путь, который есть у оригинала, клон должен воспроизвести (адрес цели в начале пути отбрасывается, путь остаётся абсолютным). Бренд ищется без учёта регистра и внутри составных имён (`acme_id`, `AcmeTasks`, `task-board`, `Task%20Board`) — по тому же правилу аудит ищет бренд в коде клона. Переименованный ключ JSON переименовывается одинаково во всём пакете: в телах запросов, схемах запросов и ответов, полях сущностей, указателях ожидаемых значений и сохраняемых переменных (`save`). Строки тел запросов, совпадающие с кодом или текстом оригинала, не меняются, но перечисляются в разделе «Предупреждения» черновика: выпуск они не блокируют, согласующий проверяет их сам. Ожидаемое значение ответа выпускается, только если это число/логическое значение или короткий идентификатор без пробелов, либо значение, которое сценарий сам отправил.
- **clean** — агент, пишущий клон. Видит только clean и released артефакты; доступ к dirty запрещён в `ArtifactStore.get`, а не соглашением, и каждая попытка пишется в журнал. Вывод тестов, который видит агент, очищается от путей машины и названий оригинала. Это разделение по данным, а не по процессу: в `LocalSandbox` код клона не изолирован от машины; README пакета доказательств указывает, была ли песочница изолирована.
- **verifier** — проверяющий код: видит всё, но в чистую зону отдаёт только короткую обезличенную обратную связь (без тел ответов и текстов оригинала).

Каждый вызов LLM, чтение и запись артефактов, выпуск, согласование и переход между этапами фиксируются в журнале `ledger.jsonl` (хэш-цепочка, проверяется `ledger-verify`). Если не указано `target_is_sandbox: true`, конвейер не пишет в цель: браузер обрывает запросы кроме GET/HEAD, которые отправляют сами страницы цели, а проверка паритета пропускает сценарии с записью. WebSocket-соединения к хостам вне `allowed_domains` браузер не открывает (они перечисляются в `skipped`), всплывающие окна закрываются сразу. Частота запросов к цели — не выше 2 в секунду при наблюдении (обход, возврат на страницу после нажатия или отправки формы, зондирование) и при проверке паритета; воспроизведение сценариев оракулом со сбросом цели (только песочница, используется бенчмарком) не ограничивается.

## Ограничения прототипа

- Поддерживается только шаблон клона `python-fastapi`; TypeScript/Next.js — отдельный план (D-006).
- Кнопки и флажки вне форм исследователь нажимает только на песочнице: каждый различимый элемент управления (тип и подпись) — один раз на страницу, всего не больше 50 нажатий за обход; одинаковые кнопки в строках списка нажимаются один раз. Нажатия, похожие на разрушающие (удалить, очистить, выйти и т. п.), разрешены, но перечисляются в журнале (`observe.explore`, `destructive_clicks`). На цели не-песочнице кнопки вне форм не нажимаются, и такое поведение может не попасть в сценарии; зондирование API (`--probe`) тоже возможно только для песочницы (D-009).
- `reverseai build` и `bench` выполняют код клона в `LocalSandbox`, который не изолирует его от вашей машины (об этом выводится предупреждение). `DockerSandbox` есть в библиотеке, но образу нужны fastapi, uvicorn и httpx; в CLI он пока не подключён.
- Веб-консоль рассчитана на одного оператора на своей машине: нет учётных записей и прав, задачи живут в памяти процесса (после перезапуска консоли статус прошлой задачи не виден, результаты этапов — в проекте). Нет долговечной оркестрации (Temporal).
- Нет входа в систему на цели (login flows), перехвата трафика не из браузера и приёма документации командой.
- Порог сходства кода (5%) и порог паритета (95% / 100%) — рабочие значения, которые должен подтвердить юрист и основатель.
- Это не юридическая консультация.
